## 1. 总体结论

### 1.1 已满足的部分

**当前项目已满足“核心细胞状态模型”的基础 E2E 训练、CLI 推理、评估与 API 服务要求。**

- 全量非 slow/gpu 测试结果为 **`1162 passed / 9 skipped / 0 failed`**，无失败项。
- `scripts/train.py` 可完成示例数据生成、预处理、模型构建、训练、checkpoint 保存、测试集评估，并**自动写出配套 `.config.yaml`**。
- `scripts/train_lightning.py` 训练结束后会导出 `best_model.pt + best_model.config.yaml`，与原生训练产物格式对齐。
- `scripts/predict.py` 单样本与 CSV 批量推理均可跑通，且优先加载 checkpoint 同目录的 `.config.yaml`，避免 config 漂移。
- `scripts/evaluate.py --model outputs/models/best_model.pt --device cpu` **可直接跑通**，生成 metrics、ROC、PR、混淆矩阵。
- FastAPI 应用已区分 `/live`（存活，HTTP 200）、`/ready`（就绪，未加载模型时 HTTP 503）、`/health`（业务状态）。
- GenKI source / 软扰动 / 两阶段解释链路在缺少 `torch_geometric` 时**优雅跳过**，不再导致测试失败。

### 1.2 尚未满足的部分

**项目尚未达到“生产级完整 E2E 就绪”**，主要限制来自运行环境与数据/模型质量：

- **运行环境与 `requirements.txt` 存在明显漂移**：
  - `scvi-tools` 实际安装版本为 `0.20.3`，不满足 `>=1.0.0`，且与当前 `anndata 0.11.4` 不兼容，导致 `import scvi` 直接失败。
  - `lion-pytorch`、`mamba-ssm`、`torch_geometric` 等可选依赖均未安装。
- **默认模型与数据为合成演示**：`prepare_data.py` 仅生成随机序列与标签，`outputs/models/best_model.pt` 是在该合成数据上训练的 toy 模型，无法代表真实生物学预测能力。
- **部分 API/部署语义仍可细化**：`/health` 在模型未加载时仍返回 HTTP 200 + `"status": "unhealthy"`，若部署方混用 `/health` 与 `/ready` 可能导致误判。

### 1.3 最终判定

| 能力维度 | 判定 |
|---|---|
| 核心细胞状态 E2E 训练 | **基本满足** |
| CLI 单样本/批量推理 | **满足** |
| 默认发布模型评估 | **满足** |
| API 基础推理服务 | **满足**（需显式初始化模型） |
| DAVF / scVI 扩展链路 | **不满足**（环境不兼容） |
| GenKI 图扰动 | **不满足**（依赖缺失，但已优雅降级） |
| 真实数据 / 生产模型 | **不满足**（当前为演示数据/模型） |

> **一句话总结**：核心训练与 CLI/API 推理链路已 E2E 就绪；运行环境依赖治理、真实数据接入与生产模型训练是下一阶段重点。

## 5. 阻塞性与高严重问题

### P1-1 运行环境与 `requirements.txt` 漂移（scvi-tools / anndata 不兼容）

**严重程度：P1（扩展能力阻塞）**

#### 证据

```text
# requirements.txt 声明
scvi-tools>=1.0.0
anndata>=0.8.0
setuptools>=68.0,<81
```

实际环境：

```text
anndata: 0.11.4
scvi-tools (dist-info): 0.20.3
```

执行 `import scvi` 报错：

```text
ImportError: cannot import name 'SparseDataset' from 'anndata._core.sparse_dataset'
```

此外：

```text
lion-pytorch: MISSING
mamba-ssm: MISSING
torch_geometric: MISSING
```

#### 影响

- `ScVIAdapter.from_trained_model()`、`ScVIAdapter.from_anndata()`、`LatentDAVF` 基因空间 workflow 实际不可用。
- `requirements.txt` 与当前环境不一致，新用户按 `pip install -r requirements.txt` 安装后仍可能遇到同样问题。
- 可选能力（Lion、Mamba、GenKI）在未安装 extras 时不可用。

#### 解决策略

1. **修正 scvi-tools / anndata 版本组合**
   - 方案 A（推荐）：升级 `scvi-tools` 到与 `anndata 0.11.x` 兼容的版本（如 `>=1.1.0` 或 `>=1.2.0`，需实测）。
   - 方案 B：若必须保留旧版 scvi-tools，则锁定 `anndata<0.11`（如 `anndata==0.10.9`）。
   - 在 `requirements.txt` 与 `setup.py extras["analysis"]` 中同时显式约束，避免未来再次漂移。

2. **在 CI 中增加环境一致性门控**
   - 运行 `pip check`。
   - 运行 `python -c "import scvi; from scvi.model import SCVI"` 作为 analysis extra 的验收测试。

3. **保持并强化懒加载与友好错误**
   - `src/models/scvi_adapter.py` 已使用懒加载并在失败时给出安装命令，继续维持。
   - 在 `scripts/finetune_davf.py` 等入口增加前置检查，缺失依赖时给出 `pip install -e .[analysis]` 提示而非堆栈。

4. **整理可选依赖 extras**
   - `setup.py` 已提供 `[api]`、`[lightning]`、`[pretrained]`、`[analysis]`、`[genki]`、`[mamba]`、`[all]`，文档和 CI 应按能力矩阵引导用户安装对应 extra，而不是默认全量安装。

5. **验收命令**

   ```bash
   pip install -e ".[analysis]"
   python - <<'PY'
   import scvi
   from scvi.model import SCVI
   print("scvi-tools ok", scvi.__version__)
   PY
   python -m pytest tests/unit/test_scvi_adapter.py tests/integration/test_davf_pipeline.py -q
   ```

### P1-2 默认模型与数据为合成演示，无法承担真实预测

**严重程度：P1（产品就绪阻塞）**

#### 证据

- `scripts/prepare_data.py` 调用 `DataLoader.load_sample_data(num_samples=500)` 生成随机序列与 4 类随机标签。
- `outputs/models/best_model.pt` 在该随机数据上训练（`max_epochs: 1`，transformer 2 层）。
- 默认评估准确率约 0.23，接近随机基线。

#### 影响

- 按 README 快速开始直接运行，用户得到的是一个“可运行但无生物学意义”的 pipeline。
- 若直接用于真实预测，会给出不可靠结果，存在误导风险。

#### 解决策略

1. **明确标注默认模型为 DEMO**
   - 在 README、API 文档、`outputs/models/README.md` 中醒目说明：`best_model.pt` 仅为端到端冒烟测试模型，不代表真实预测能力。

2. **提供真实数据接入文档与示例**
   - 说明输入 CSV 必须包含的列：`id`、`sequence`、`ptm_sites`（JSON 列表）、`cell_state`。
   - 提供从 UniProt / dbPTM / PhosphoSitePlus 下载并格式化的示例 notebook 或脚本。

3. **训练并发布真实模型（如业务需要）**
   - 在真实 PTM + 细胞状态数据集上训练后，替换或并存 `outputs/models/best_model.pt`。
   - 发布时同步提供 `best_model.config.yaml`、训练数据版本、模型卡片（model card）。

4. **增加数据质量检查**
   - 在 `DataPreprocessor` 或训练入口增加标签分布、序列长度、PTM 位点合法性校验，避免用户在低质量数据上训练后误以为模型有效。

## 6. 中等严重问题

### P2-1 API `/health` 语义仍可能误导部署

**严重程度：P2（部署风险）**

#### 证据

未加载模型时：

```text
GET /api/v1/health -> 200 {"status": "unhealthy", "model_loaded": False}
GET /api/v1/ready  -> 503 {"detail": "模型未初始化"}
GET /api/v1/live   -> 200 {"status": "alive"}
```

#### 影响

- 若负载均衡器/监控仍指向 `/health` 做 readiness 判断，会把“未加载模型”实例判定为健康。
- 当前 `Dockerfile` 已使用 `/ready`，风险可控，但文档不足。

#### 解决策略

1. 在 `README.md`、`API_DOCUMENTATION.md` 与 `/docs` 中明确：
   - `/live`：进程存活探针。
   - `/ready`：服务就绪探针（用于 Kubernetes readinessProbe、Docker HEALTHCHECK）。
   - `/health`：遗留/综合健康检查，不用于流量接入判断。
2. 或调整 `/health` 行为：模型未加载时返回 503，完全等价于 `/ready`；将 `/live` 作为存活探针。此方案更严格，但会改变现有 API 契约，需同步修改测试。
3. 在 `/docs`（Swagger）中为三个端点添加描述，降低误用概率。

### P2-2 可选依赖未安装导致部分能力降级

**严重程度：P2（功能降级）**

#### 证据

```text
lion-pytorch: MISSING -> LightningModule 中 lion 优化器回退到 AdamW
mamba-ssm: MISSING    -> MambaEncoder 使用 fallback 实现
torch_geometric: MISSING -> GenKI source backend 跳过
```

#### 影响

- 用户按最小依赖安装时，无法使用 Lion、原生 Mamba、GenKI 图扰动。
- 当前代码已有 fallback 或跳过逻辑，核心链路不受影响。

#### 解决策略

1. 在 README 中区分“核心安装”与“全量安装”：

   ```bash
   pip install -r requirements.txt          # 核心 + 大部分能力
   pip install -e ".[all]"                  # 全量能力
   ```

2. 在对应脚本入口增加依赖检查并打印安装命令，例如：

   ```text
   GenKI source backend 不可用：缺少 torch_geometric。请执行 pip install -e ".[genki]"
   ```

3. CI 中增加 optional-extra 矩阵：一组只安装核心依赖并运行跳过 optional 的测试；另一组安装 `[all]` 并强制所有 optional 测试通过。
