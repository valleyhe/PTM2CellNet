# PTM2CellNet 当前代码 E2E 训练与推理现状复核

日期：2026-07-02  
范围：当前工作树中的训练 CLI、推理 CLI、Lightning 训练、预训练模型训练、API 初始化/预测、checkpoint 合约、数据预处理与现有测试。

## 结论

当前代码已经满足“小模型工程级 E2E 闭环”的基本要求：原生 `scripts/train.py -> scripts/predict.py` 可以完成训练、导出、加载与推理；`scripts/train_lightning.py` 也已经导出可被推理 CLI 消费的 `best_model.pt + best_model.config.yaml`，并修复了非默认类别数的标签映射问题。API 的手动 `/api/v1/initialize` 路径具备较严格的 checkpoint/config 匹配校验。

但项目尚未达到“完整生产/真实生物学 E2E 训练和推理就绪”。主要剩余风险集中在：API 启动时自动初始化仍可能用错误标签语义；预训练模型训练脚本没有统一 artifact/标签/推理合约；当前验证主要覆盖 CNN 小模型和合成样例数据；依赖和默认配置仍偏研究环境，不能保证用户从空环境安装后稳定跑通；真实数据 provenance、评估门槛、模型卡和发布门禁仍不足。

## 尚未达到完整 E2E 就绪的主要问题

### P0-1：API 启动自动初始化可能使用错误标签语义

严重程度：阻塞性  
影响范围：Docker/K8s/uvicorn 启动时通过环境变量自动加载模型的生产部署路径。  
相关文件：`src/api/app.py`

现象：

- `_try_auto_initialize()` 默认读取 `PTM2CELLNET_CELL_STATES`，若未设置则使用硬编码顺序 `proliferation,differentiation,apoptosis,quiescence`（约第 47-51 行）。
- 即使训练 artifact 的 config/manifest 含有真实 `data.cell_states`，自动初始化最终仍使用环境变量解析出的 `cell_states` 调用 `initialize_model()`（约第 104-107 行）。
- 这与 `/api/v1/initialize` 不一致；手动初始化会优先使用 config 中的 `data.cell_states`（`src/api/routes/initialize.py` 约第 117 行）。

风险：

- 3 类、2 类或自定义标签顺序模型启动后可能加载成功，但预测响应中的标签名被错误解码。
- 对 4 类但顺序不同的模型，错误更隐蔽：不会崩溃，只会给出语义错误的细胞状态。

解决策略：

1. 修改 `_try_auto_initialize()` 的标签解析优先级：
   - 第一优先级：config 中的 `data.cell_states`。
   - 第二优先级：sibling `artifact_manifest.json` 中的 `cell_states`。
   - 第三优先级：显式 `PTM2CELLNET_CELL_STATES`，并记录 warning。
   - 禁止无显式配置时使用硬编码默认标签。
2. 在自动初始化中执行一致性校验：
   - `len(cell_states) == config["model"]["num_classes"]`。
   - 若 checkpoint logits 维度可从 predictor 权重推断，也应与 `len(cell_states)` 一致。
3. 增加 API startup E2E 测试：
   - 训练一个 3 类 artifact。
   - 设置 `PTM2CELLNET_CHECKPOINT` 和 `PTM2CELLNET_CONFIG`，不设置 `PTM2CELLNET_CELL_STATES`。
   - 触发 FastAPI lifespan。
   - 断言 `STATE.cell_states` 等于 artifact config 中的 3 类标签。
   - 调用 `/api/v1/predict`，断言概率字典只包含这 3 个标签。

验收命令：

```bash
pytest tests/unit/test_api_auto_initialize.py tests/e2e/test_train_predict_cli.py -q
```

### P0-2：预训练模型训练脚本未纳入统一推理 artifact 合约

严重程度：阻塞性  
影响范围：`scripts/train_pretrained.py` 训练 ESM-2/ProtBERT 等真实候选模型后的推理可用性。  
相关文件：`scripts/train_pretrained.py`

现象：

- `scripts/train_pretrained.py` 在预处理后直接创建模型，没有派生并同步 `data.cell_states` / `data.label_to_idx` / `model.num_classes`（约第 158-169 行）。
- 该脚本没有导出与 `train.py` / `train_lightning.py` 对齐的裸 `best_model.pt`、`best_model.config.yaml`、`artifact_manifest.json`（约第 262-276 行仅测试并结束）。
- 它有 tokenizer 注入逻辑（约第 171-185 行），但产物没有被 `scripts/predict.py` 的通用推理入口验证。
- `configs/pretrained/esm2_8m.yaml` 默认 `model.num_classes: 2`，真实数据类别数不一致时可能训练/评估指标或推理配置错位。

风险：

- 预训练模型是更接近真实科研/生产的路径；当前却没有与主推理入口闭环。
- 用户可能得到 Lightning `.ckpt`，但缺少 sibling config/manifest，`predict.py` 无法可靠解析标签和模型结构。

解决策略：

1. 抽取共享训练产物导出函数，例如 `src/training/artifacts.py`：
   - `derive_and_apply_label_mapping(config, train_df)`
   - `export_inference_artifact(model_or_lightning_module, config, output_dir, metadata)`
   - `write_artifact_manifest(...)`
2. 让 `train.py`、`train_lightning.py`、`train_pretrained.py` 共用同一套导出逻辑。
3. `train_pretrained.py` 在创建模型前同步标签映射和 `model.num_classes`。
4. 训练完成后导出：
   - `best_model.pt`
   - `best_model.config.yaml`
   - `artifact_manifest.json`
   - tokenizer/model family 元信息，例如 `encoder_type`、HF model name、cache/source。
5. 增加预训练 smoke E2E：
   - 使用 monkeypatch/dummy HF model 或本地 tiny mock，避免 CI 下载大模型。
   - 运行 `train_pretrained.py --model esm2_8M --max-epochs 1`。
   - 断言导出 artifact 可被 `predict.py` 加载并推理。

验收命令：

```bash
pytest tests/e2e/test_pretrained_train_predict_cli.py tests/unit/test_pretrained_encoders.py -q
```

### P1-1：当前 E2E 主要证明工程链路，不证明真实生物学模型就绪

严重程度：高  
影响范围：科研结论、对外演示、生产部署。

现状：

- E2E 测试明确使用小模型 CNN、小数据、CPU、1 epoch（`tests/e2e/test_train_predict_cli.py` 约第 1-9 行）。
- 默认样例数据 `data/raw/sample_data.csv` 是合成样例，训练脚本也会把 sample/synthetic 标记为 demo。
- 训练产物已有 `model_kind=demo` / `not_for_biological_use` 标记，但没有真实数据集、真实 checkpoint、最低评估阈值和发布门禁。

风险：

- 可以证明“代码跑通”，不能证明“模型可用”。
- 任何基于 sample fixture 的预测都不应被解释为真实 PTM-细胞状态关系。

解决策略：

1. 定义真实 E2E 数据契约：
   - 必需列：`sequence`、`ptm_sites`、`cell_state`。
   - 可选但推荐列：`protein_accession`、`gene_symbol`、`source_db`、`evidence_level`、`split_group`。
   - 明确 PTM 位点 position 是 1-based，且需与序列长度一致。
2. 加入真实数据 profile 报告：
   - 样本数、类别分布、PTM 类型分布、序列长度分布、重复率、同源泄漏检查。
3. 设立发布门禁：
   - 真实数据训练产物必须 `model_kind=real`。
   - 必须有 holdout test metrics。
   - 必须达到配置化阈值，例如 macro-F1/AUROC/AUPR 下限。
   - 指标低于阈值时仍可保存实验产物，但不能标记为 deployable。
4. 在 `artifact_manifest.json` 增加：
   - dataset hash。
   - split strategy。
   - metrics summary。
   - intended_use / limitations。
   - `deployable: true/false`。

### P1-2：依赖声明把重型可选能力变成默认安装风险

严重程度：高  
影响范围：新环境安装、CI、CPU-only 用户、Docker 构建。

现象：

- `requirements.txt` 把 `scvi-tools`、`sspa`、`mamba-ssm` 等放入默认依赖（约第 20-33 行、第 61 行）。
- 注释称 `mamba-ssm` 是 optional，但它仍在默认 requirements 中。
- Mamba 和 scVI 生态对 CUDA、PyTorch、编译工具链、Python 版本更敏感，容易让基础 CNN/Transformer E2E 安装失败。

风险：

- 用户可能连最小训练/推理 smoke test 都因可选扩展依赖安装失败而无法启动。
- “E2E 可运行”在当前开发机成立，但不一定能迁移到干净环境。

解决策略：

1. 拆分依赖：
   - `requirements-core.txt`：训练/推理/API 最小闭环。
   - `requirements-pretrained.txt`：transformers/peft/tokenizers。
   - `requirements-mamba.txt`：mamba-ssm/einops 等。
   - `requirements-analysis.txt`：scvi/anndata/sspa/GenKI/DAVF。
2. `setup.py` extras 与这些文件保持一致：
   - `pip install -e .[core]`
   - `pip install -e .[pretrained]`
   - `pip install -e .[mamba]`
   - `pip install -e .[analysis]`
   - `pip install -e .[all]`
3. Dockerfile 默认只安装 core；GPU/Mamba/DAVF 用单独 target 或 build arg。
4. CI 增加最小干净环境 job：
   - 安装 core。
   - 跑 `tests/e2e/test_train_predict_cli.py`。

### P1-3：默认配置不适合作为用户首次 E2E 入口

严重程度：高  
影响范围：首次运行体验、文档 quickstart、CPU 环境。

现象：

- `configs/default.yaml` 默认是 transformer、hidden_dim 256、6 层、100 epoch（约第 45-69 行）。
- E2E 测试实际使用临时生成的小 CNN 配置，而不是默认配置。
- 如果用户按直觉运行 `python scripts/train.py --data data/raw/sample_data.csv`，训练成本明显高于 smoke test 期望。

风险：

- 工程上可跑通，但默认入口不够“快速验证”。
- 用户难以区分 smoke config、research config、production config。

解决策略：

1. 新增明确入口配置：
   - `configs/smoke/cnn_cpu.yaml`
   - `configs/research/transformer.yaml`
   - `configs/production.yaml`
2. README 和 quickstart 只使用 smoke config 做首次 E2E：

```bash
python scripts/train.py --config configs/smoke/cnn_cpu.yaml --data data/raw/sample_data.csv --output outputs/smoke
python scripts/predict.py --model outputs/smoke/models/best_model.pt --sequence ACDEFGHIKLMNPQRSTVWY --device cpu
```

3. 默认配置可以保留研究用途，但文件名不应暗示“首次运行默认推荐”。
4. CLI 可在未显式传 `--config` 时提示当前默认配置较重，并建议 smoke config。

### P2-1：测试覆盖仍缺少若干真实部署和真实推理边界

严重程度：中高  
影响范围：回归风险。

缺口：

- API startup auto-init 标签语义未覆盖。
- `train_pretrained.py -> predict.py` 未覆盖。
- 干净环境安装未覆盖。
- 自定义 `ptm_types` 训练后推理语义一致性覆盖不足。
- 真实数据 contract/schema validation 未形成独立 E2E。
- 批量推理空 CSV 的 CLI 行为需要明确：现在 API batch 空列表有处理，但 CLI batch 读取空 CSV 后 `_predict_in_batches` 会在无 chunk 情况下返回空列表，输出空表是否符合预期需要测试锁定。

解决策略：

1. 增加测试矩阵：
   - native CNN CPU smoke。
   - Lightning CNN CPU smoke。
   - API `/initialize` smoke。
   - API startup auto-init smoke。
   - pretrained mocked-HF smoke。
   - custom labels/custom PTM types smoke。
2. 把 `tests/e2e` 的目标从“单一 happy path”扩展为“所有公开入口的最小闭环”。
3. 对生产相关路径增加 negative tests：
   - 缺 config。
   - config 标签数与 checkpoint logits 不一致。
   - artifact manifest 缺失。
   - demo 模型被部署时应在 `/model/info` 暴露 warning。

## 建议实施顺序

1. 先修 `P0-1 API auto-init 标签语义`。这是生产部署路径中最容易产生静默错误的点。
2. 再统一 `train_pretrained.py` artifact 合约。真实模型路径必须能被同一个 `predict.py` 和 API 消费。
3. 拆分依赖与 smoke 配置，确保干净环境中的最小 E2E 可复现。
4. 增加真实数据/发布门禁字段，避免把 demo 产物误当可用模型。
5. 扩展 E2E 测试矩阵，并把每个公开入口都纳入回归保护。
