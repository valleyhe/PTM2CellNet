# PTM2CellNet 当前代码 E2E 训练与推理复核报告

日期：2026-07-01  
范围：当前工作树中的训练脚本、推理脚本、API 初始化/预测、数据预处理、模型导出、checkpoint 加载与现有 E2E 测试。

## 结论

当前代码已经满足“最小原生 E2E 闭环”的要求：`scripts/train.py` 可以在小型 CSV 数据上训练模型，导出 `best_model.pt` 与 `best_model.config.yaml`；`scripts/predict.py` 可以优先读取 checkpoint 同目录配置，使用持久化的 `data.cell_states` 解码预测结果；API `/api/v1/initialize` 已经能严格加载匹配 checkpoint，并对形状/键不匹配返回 400。

但项目尚未达到“完整、稳定、生产可用的 E2E 训练和推理”要求。主要阻塞点集中在 Lightning 训练产物与推理合约不一致、小数据/重复数据场景失败模式不清晰、CLI/API 推理预处理状态未完整继承训练配置，以及 E2E 覆盖范围仍偏窄。

### 额外探针

1. 使用 3 类数据训练 `scripts/train_lightning.py`，配置中保留默认 `model.num_classes: 4`。训练和导出成功，但导出的 `best_model.config.yaml` 同时包含：

```yaml
data:
  cell_states: [a, b, c]
model:
  num_classes: 4
```

随后执行：

```bash
python scripts/predict.py --model /tmp/.../models/best_model.pt \
  --sequence ACDEFGHIKLMNPQRSTVWY --device cpu --output /tmp/.../pred.csv
```

失败，核心错误：

```text
size mismatch for predictor.classifier.weight:
copying a param with shape torch.Size([4, 128]) from checkpoint,
the shape in current model is torch.Size([3, 128])
```

这证明 Lightning 训练产物在非 4 类数据上不能被当前推理 CLI 消费。

2. 使用重复序列小数据运行 `scripts/train_lightning.py`。预处理默认去重后 60 行变成 1 行，`drop_last=True` 导致没有训练 batch，随后 `trainer.test()` 因没有 best checkpoint 失败：

```text
Trainer.fit stopped: No training batches.
ValueError: .test(ckpt_path="best") is set but ModelCheckpoint is not configured to save the best model.
```

这证明 Lightning CLI 在小数据/重复数据下没有足够早、足够可操作的 fail-fast 保护。

3. 使用原生 `train.py` 训练 2 类、`max_sequence_length=64` 的小模型，并带 PTM 位点执行 `predict.py`，命令成功。这说明原生路径目前能跑通；但 `predict.py` 调用 `initialize_model(model, cell_states, device)` 时未传入训练配置，API 预处理状态会退回默认 `max_sequence_length=1000` 与默认 PTM 类型。该问题未在此探针中触发崩溃，但会造成训练/推理张量长度和 PTM 类型映射不严格一致。

## 尚未达到要求的主要问题

### P0-1：Lightning 训练产物在非默认类别数上无法 E2E 推理

严重程度：阻塞性  
影响范围：`scripts/train_lightning.py -> scripts/predict.py`，也影响 API 使用 Lightning 导出的 `best_model.pt`。

现象：

- `train_lightning.py` 在创建模型前没有基于训练数据标签更新 `config.model.num_classes`。
- `_export_inference_artifact()` 只写入 `data.cell_states` / `data.label_to_idx`，没有同步 `model.num_classes`。
- `predict.py` 会根据 `len(data.cell_states)` 覆盖 `model.num_classes` 后构建推理模型。
- 当训练时模型输出维度是 4、推理时根据 3 个标签构建 3 类模型时，checkpoint 加载必然形状不匹配。

根因：

- Lightning 路径的模型构建早于 `data_module.setup()`，未把训练集标签空间作为模型结构的单一事实来源。
- 原生 `train.py` 已经做了 `config.set("model.num_classes", len(cell_states))`，Lightning 路径没有同等逻辑。

解决策略：

1. 在 `train_lightning.py` 完成预处理后、创建模型前，显式构建一次训练标签映射。
   - 可以直接用 `sorted(train_df["cell_state"].unique())`，与 `PTMDatasetBase` 当前规则保持一致。
   - 更稳妥方式是实例化训练 dataset 或调用一个共享 helper，避免规则分叉。
2. 在创建 `PTM2CellNet` 与 `PTM2CellNetLightning` 前写入：
   - `config.set("data.cell_states", cell_states)`
   - `config.set("data.label_to_idx", label_to_idx)`
   - `config.set("model.num_classes", len(cell_states))`
3. `_export_inference_artifact()` 保存配置前再次校验：
   - `config.get("model.num_classes") == len(config.get("data.cell_states"))`
   - 不一致则直接抛出错误，不导出不可推理 artifact。
4. `PTM2CellNetLightning._setup_metrics()` 应读取同步后的 `model.num_classes`，避免 torchmetrics 类别数与实际 logits 维度不一致。
5. 新增 E2E 测试：
   - 构造 3 类数据，配置初始 `model.num_classes: 4`。
   - 运行 `train_lightning.py --max-epochs 1 --batch-size 8 --accelerator cpu` 或临时 CPU 配置。
   - 断言导出的 `best_model.config.yaml` 中 `model.num_classes == 3`。
   - 用导出的 `best_model.pt` 执行 `predict.py`，断言成功且输出包含 3 个概率列。

验收命令建议：

```bash
pytest -q tests/e2e/test_train_predict_cli.py tests/e2e/test_api_initialize_checkpoint.py
pytest -q tests/integration/test_train_lightning_script.py
```

并新增一个真实 Lightning 训练到推理测试，不能只测 `--help`。

### P0-2：Lightning 小数据/重复数据场景会在训练后期以不清晰方式失败

严重程度：阻塞性  
影响范围：小样本调试、CI smoke test、用户首次试跑、重复序列较多的数据。

现象：

- 预处理默认 `remove_duplicates=True`，重复序列数据可能被大幅压缩。
- `PTMLightningDataModule.train_dataloader()` 固定 `drop_last=True`。
- 当训练集样本数小于 batch size 时，Lightning 没有训练 batch。
- 之后 `trainer.test()` 默认试图使用 best checkpoint，但没有 best checkpoint，报错位置离真实原因较远。

根因：

- 训练前没有检查 dataloader 是否至少有 1 个 batch。
- `drop_last=True` 对小数据 smoke test 不友好。
- 验证/测试集为空时仍继续执行 checkpoint monitor 和 test 流程。

解决策略：

1. 在 Lightning 训练前增加运行前检查：
   - 预处理后 `len(train_df) > 0`。
   - 若 `drop_last=True`，要求 `len(train_df) >= batch_size`。
   - 若启用 checkpoint 且 `monitor=val_loss`，要求 `len(val_df) > 0`。
   - 若执行 `trainer.test()`，要求 `len(test_df) > 0`，否则跳过并输出明确 warning。
2. 将 `drop_last` 改为配置项，默认对生产训练可为 `True`，对 smoke test/CPU 示例建议为 `False`。
3. 当没有 best checkpoint 时：
   - `trainer.test(lightning_model, datamodule=data_module, ckpt_path=None)` 使用当前模型；或
   - 明确跳过 test，并给出“没有训练 batch / 没有 best checkpoint”的错误。
4. 数据质量预检应提前提示“去重后样本数过少”，而不是等到 Lightning dataloader 阶段。

建议测试：

- 重复序列数据，验证脚本在训练前输出可操作错误。
- `batch_size > len(train_df)` 且 `drop_last=True`，验证 fail-fast。
- `drop_last=False` 的小数据 smoke test，验证能完成训练与导出。

### P1-1：CLI 推理复用 API 预处理，但没有把训练配置注入 API 状态

严重程度：高  
影响范围：`scripts/predict.py` 单样本和批量推理，尤其是非默认 `max_sequence_length`、自定义 `ptm_types`、自定义 amino acid 配置。

现象：

- `predict.py` 加载 config 后构建模型，但调用：

```python
initialize_model(model, cell_states, device)
```

- `initialize_model()` 的 `config` 参数未传入，因此 `STATE.feature_extractor`、`STATE.max_sequence_length`、`STATE.ptm_type_to_idx` 使用默认值。
- 当前原生探针未崩溃，但训练和推理预处理长度可能不一致。例如训练 config 是 `max_sequence_length=64`，推理预处理仍可能生成 1000 长度输入。

风险：

- PTM 类型索引与训练时不一致会改变模型实际输入语义。
- 推理序列长度与训练长度不一致会引入分布偏移，长序列还会增加不必要计算。
- 未来如果模型组件不再 clamp positions，可能变成运行时错误。

解决策略：

1. 修改 `scripts/predict.py`：

```python
initialize_model(model, cell_states, device, config=config.to_dict())
```

2. 增加单元/集成测试：
   - 训练或构造 `max_sequence_length=64` 模型。
   - 调用 CLI/API 预处理后断言 `sequence.shape[-1] == 64`。
   - 使用自定义 `data.ptm_types`，断言 PTM type index 与 config 一致。
3. 避免 CLI 直接依赖 API 全局状态作为预处理的唯一入口；中期应抽出共享 `InferencePreprocessor(config)`，CLI 和 API 都使用它。

### P1-2：批量 CLI 输出缺少每类概率列，单样本/批量输出契约不一致

严重程度：高  
影响范围：批量推理结果消费、下游评估、校准分析、可解释性分析。

现象：

- 单样本输出包含 `prob_<state>` 概率列。
- 批量输出只有 `id`、`sequence`、`ptm_count`、`predicted_cell_state`、`confidence`。
- 现有 E2E 测试只验证单样本概率列和批量 `ptm_count`，未覆盖批量概率列。

风险：

- 下游无法从批量结果恢复完整概率分布。
- 单样本和批量推理输出 schema 不一致，容易造成用户脚本分叉。

解决策略：

1. `_predict_in_batches()` 返回完整 `probabilities`，而不仅是 `predictions/confidences`。
2. 批量结果每行增加：

```python
{f"prob_{state}": float(probs[i, j]) for j, state in enumerate(cell_states)}
```

3. 更新 E2E 测试，断言批量输出也包含每个 `prob_<state>`。

### P1-3：训练/推理配置契约仍缺少 artifact manifest

严重程度：高  
影响范围：多训练入口、多模型变体、生产部署。

现状：

- 当前依赖 `best_model.pt` + sibling `best_model.config.yaml`。
- 该方式已经比默认 config 安全，但仍缺少明确 artifact manifest。

风险：

- 无法快速判断 checkpoint 的训练入口、代码版本、标签映射 hash、模型结构 hash、预处理版本。
- 多个脚本并行输出到同一目录时容易覆盖 `best_model.pt`。
- API 初始化只能在加载时报 shape mismatch，不能在加载前给出更清楚诊断。

解决策略：

1. 每次训练导出 `artifact_manifest.json`：
   - `checkpoint_path`
   - `config_path`
   - `training_entrypoint`
   - `model_class`
   - `model_signature`
   - `num_classes`
   - `cell_states`
   - `ptm_types`
   - `max_sequence_length`
   - `git_commit` 或 dirty 状态摘要
   - `created_at`
2. `predict.py` 和 `/initialize` 优先读取 manifest，再回退 sibling config。
3. manifest 中的 `num_classes`、`cell_states`、checkpoint classifier shape 必须一致，否则 fail-fast。

### P2-1：E2E 测试矩阵仍不足

严重程度：中高  
影响范围：回归风险。

当前已有良好覆盖：

- 原生训练到 CLI 推理。
- API initialize strict loading。
- checkpoint 格式提取。

缺口：

- 没有真实 Lightning 训练到 CLI/API 推理 E2E。
- 没有非 4 类标签数据的训练/推理回归测试。
- 没有自定义 `max_sequence_length` / `ptm_types` 的推理预处理一致性测试。
- 没有批量推理概率列测试。
- 没有 API `/predict` 在 `/initialize` 后的真实请求测试。
- 没有 pretrained encoder 的离线/跳过策略 E2E；如果依赖 Hugging Face 网络或缓存，CI 应显式 skip 或 mock。

解决策略：

建立分层测试矩阵：

1. Smoke E2E（每次 CI）：
   - 原生 CNN CPU 1 epoch。
   - Lightning CNN CPU 1 epoch。
   - API initialize + `/predict`。
2. Contract E2E：
   - 2 类、3 类、4 类标签。
   - 自定义 `max_sequence_length`。
   - 自定义 `ptm_types`。
   - 单样本和批量输出 schema 一致性。
3. Optional/slow E2E：
   - ESM/ProtBERT，只在缓存存在或显式环境变量开启时运行。
   - DAVF/GenKI 集成，只使用固定 fixture。

### P2-2：API 路由模块存在同名文件/包遮蔽，维护风险仍在

严重程度：中  
影响范围：长期维护、导入歧义。

现状：

- 同时存在 `src/api/routes.py` 和 `src/api/routes/` 包。
- `routes.py` 已经改为薄包装并重新导出子包接口。

风险：

- Python 导入优先级和工具索引可能产生歧义。
- 新贡献者可能误改 `routes.py`，以为它是主实现。

解决策略：

1. 保留当前薄包装短期可接受。
2. 中期迁移所有导入到 `src.api.routes` 子包明确路径。
3. 最终删除或重命名 `src/api/routes.py`，避免同名模块/包共存。

## 建议修复优先级

### 第一优先级：修复 Lightning artifact 合约

目标：所有训练入口导出的 artifact 都能被 `predict.py` 和 API 严格加载。

实施步骤：

1. 抽出共享函数，例如 `src/data/labels.py`：

```python
def derive_label_mapping(df, label_col="cell_state"):
    labels = sorted(df[label_col].dropna().astype(str).unique())
    if len(labels) < 2:
        raise ValueError(...)
    return labels, {label: i for i, label in enumerate(labels)}
```

2. `train.py` 和 `train_lightning.py` 都使用同一个 helper。
3. Lightning 创建模型前同步 `data.cell_states`、`data.label_to_idx`、`model.num_classes`。
4. `_export_inference_artifact()` 增加一致性断言。
5. 新增 3 类 Lightning E2E 测试。

### 第二优先级：修复推理预处理配置注入

目标：训练配置中的序列长度、PTM 类型、氨基酸表在 CLI/API 推理中一致生效。

实施步骤：

1. `predict.py` 调用 `initialize_model(..., config=config.to_dict())`。
2. 新增测试断言 CLI 推理预处理长度等于训练配置。
3. 中期抽出无全局状态的 `InferencePreprocessor`，避免 CLI 依赖 API router state。

### 第三优先级：加强 Lightning 小数据 fail-fast 与测试流程

目标：不再出现 “No training batches” 后才在 `trainer.test()` 崩溃的错误链。

实施步骤：

1. 训练前校验 `len(train_df)`、`len(val_df)`、`len(test_df)` 与 batch/checkpoint/test 配置。
2. `drop_last` 配置化。
3. 没有验证集时禁用 `val_loss` monitor 或直接 fail-fast。
4. 没有测试集时跳过 `trainer.test()` 并输出明确日志。

### 第四优先级：补齐推理输出与测试矩阵

目标：单样本、批量、API 的输出契约一致且被测试锁定。

实施步骤：

1. 批量 CLI 输出补齐每类概率列。
2. API `/predict` after `/initialize` 加入 E2E 测试。
3. 加入 2/3/4 类、非默认长度、自定义 PTM 类型的 contract tests。

| Lightning `train_lightning.py -> predict.py` | 未满足 | 非默认类别数会导出不可推理 artifact |
| 非默认标签数 | 原生基本满足，Lightning 未满足 | 3 类 Lightning 探针已复现失败 |
| 非默认预处理配置一致性 | 部分满足 | CLI 推理未把 config 注入 API state，存在一致性风险 |
| 小数据/重复数据 smoke run | 未满足 | Lightning 会因去重/drop_last/test checkpoint 链式失败 |
| 生产级 artifact 可追溯性 | 未满足 | 缺少 manifest 和结构 hash |

综合判断：当前代码可以支持受限场景下的 E2E 演示和原生训练/推理闭环，但尚未满足完整 E2E 训练和推理要求。需要优先修复 Lightning artifact 合约、推理预处理配置注入、小数据 fail-fast 和 E2E 测试矩阵后，才能认为项目达到稳定 E2E 可用状态。
