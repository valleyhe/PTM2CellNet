## 6. 阻塞性与高严重性问题及解决策略

### 6.1 ⛔ 阻塞性：无 CI/CD 系统（严重程度：高）

**问题**: `.github/` 目录不存在，项目没有任何 CI/CD 配置。所有测试需要通过手动命令在本地运行，无法保证提交质量。

**影响范围**:
- 新提交无法自动验证
- 回归问题在合并后才发现
- 协作开发缺乏质量门禁

**解决策略**:
```
1. 创建 .github/workflows/ci.yml，包含：
   - 触发条件: push to main, PR to main
   - Python 3.10 环境
   - 安装核心依赖 (requirements-core.txt)
   - 运行 pytest tests/unit/ -m "not gpu" --timeout=120 -x
   - 运行 mypy src/ (逐步增加覆盖)
   
2. 创建 .github/workflows/full-test.yml（手动触发）:
   - 完整依赖安装
   - 全部测试（跳过 gpu 标记）
   
3. 创建 .github/workflows/lint.yml:
   - ruff check + format
   - mypy src/
```

### 6.2 🟠 高严重性：`Any` 类型标注泛滥（严重程度：高）

**问题**: ~410 处 `Any` 标注分布在 55 个文件中，核心问题是 `Dict[str, Any]` 模式（~180 处）使类型检查器无法验证字典内容的正确性。

**影响范围**:
- 类型安全低下，运行时错误难以通过静态分析发现
- 影响 API 边界的数据验证
- 代码重构风险高

**解决策略 (分三阶段)**:
```
阶段 1（立即可做）: Protocol 类替代 Dict[str, Any]
  - src/training/artifacts.py → 定义 ArtifactMetadata Protocol
  - src/evaluation/evaluators.py → 定义 EvalResult TypedDict
  - src/data/loaders.py → 定义 LoaderResult TypedDict
  预期减少 Any ~80 处

阶段 2（1-2 轮）: dataclass 替代动态字典
  - src/utils/io.py → 序列化配置 TypedDict
  - src/models/external_tools.py → 外部工具响应 dataclass
  - src/models/davf_checkpoint_utils.py → CheckpointMetadata dataclass
  预期减少 Any ~60 处

阶段 3（持续）: 泛型参数化
  - src/evaluation/explainers.py → TypeVar 泛型化
  - src/integration/genki_adapter.py → VGAE 协议 Protocol
  预期减少 Any ~40 处
```

### 6.3 🟠 高严重性：宽 `except Exception:` 捕获（严重程度：中高）

**问题**: 89 处宽捕获，其中约 30% 可改用更精确的异常类型。

**影响范围**:
- 可能隐藏真正的编程错误
- 调试困难（异常堆栈被吞没）
- 安全敏感代码中可能掩盖攻击

**解决策略**:
```
优先级 1（API 层）:
  - src/api/routes/predictions.py: 6 处 → 区分 ValueError/KeyError/RuntimeError
    与 HTTPException，对未知异常保留 500 但记录详细日志
  
优先级 2（外部工具）:
  - src/models/external_tools.py: 4 处 → 区分 requests 异常（ConnectionError/Timeout/HTTPError）
    与业务逻辑异常
  
优先级 3（分析管道）:
  - src/analysis/variant_workflow.py: 4 处 → 按步骤区分异常类型
  - src/analysis/pathway_integration.py: 4 处 → API 异常与数据异常分离
```

### 6.4 🟡 中高严重性：`mypy: disable-error-code` 粗粒度抑制

**问题**: 6 个文件的行首抑制 + 11 个模块的 pyproject.toml 覆盖，抑制范围偏大。

**影响范围**:
- 被抑制的模块失去了类型检查的保护
- 新引入的类型错误不会被发现
- 随代码演进，抑制区域可能扩大

**解决策略**:
```
短期：在每个模块中定义 1-2 个 __init__.py 级别的 Protocol/TypedDict
  解决类型传播问题，测试是否可缩小抑制范围

中期：逐个文件移除抑制，先用 mypy --strict 跑全量覆盖报告
  按 pyproject.toml 中的模块列表进行
  
长期：将抑制原因记录到文件注释中，设定期限复查
```

### 6.5 🟡 中严重性：Mamba SSM 串行实现

**问题**: `mamba_encoder.py` 中 SSM 递推是 Python `for` 循环 [`src/models/mamba_encoder.py`]，因递推状态依赖无法简单向量化。

**影响范围**:
- 推理速度瓶颈（长序列场景尤为明显）
- GPU 利用率不足

**解决策略**:
```
选项 A（推荐）: 使用 torch.compile 或 CUDA graph 包装循环
  预期提速 2-5x，改动最小

选项 B（长期）: 集成 mamba-ssm CUDA kernel（mamba_ssm 包）
  需处理额外依赖（已在 requirements-mamba.txt 中）
  
选项 C（中期）: 使用 torch.jit.script 或 Triton 手写 kernel
  最佳性能但开发成本高
```

### 6.6 🟡 中严重性：滑动窗口逻辑重复

**问题**: `long_sequence.py` 中 ESM2 和 ESM3 的 `encode_sequences()` 方法存在重复的滑动窗口处理逻辑。

**影响范围**:
- 代码维护负担（修改窗口逻辑须同步修改两处）
- 潜在的行为偏差

**解决策略**:
```
提取共享基类或工具函数:
  class SlidingWindowHandler:
      def __init__(self, window_size, overlap, pooling_strategy)
      def process(self, model, sequences) -> Tensor
  
ESM2Encoder 和 ESM3Encoder 均委托给该 handler
预期减少 ~80 行重复代码
```
